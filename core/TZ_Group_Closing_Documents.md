
# ТЗ: Групповой выпуск закрывающих документов (мульти-объект, один ИНН)

Версия: 2025-10-01

## 0. Архитектура и ограничения

- Жизненный цикл, модели, хранение и GraphQL остаются неизменными. Используем текущую мутацию создания закрытия (`adminCreateClosingDocumentByIdHotelAndStartEndDate`) и текущие модели `ClosingDocument` и `ClosingDocumentFile`. Путь хранения в MinIO сохраняется прежним.
- В ответ фронту возвращаем тот же объект `closingDocument { id, hotel, closingDatetime, files { name, path, amount, number } }`.
- Меняем только **сбор строк** и **рендер содержимого файлов** при выборе нескольких объектов (`Hotel`) с одинаковым ИНН.

## 1. Вход и общие правила

### 1.1 Входные параметры (как сейчас)
- `id` (ID базового отеля для сущности закрытия), `startDate`, `endDate`, `closingDate`, `joinPaymentDocs`.
- Параметры периода и даты документа приходят с фронта. Нумерация — по текущим правилам.

### 1.2 Мульти-объектный сценарий
- Пользователь выбирает несколько `Hotel` с **одинаковым** ИНН.
- Внутри сборщика формируем **единый список строк** по всем выбранным объектам. В БД по-прежнему создаётся **один** `ClosingDocument` с набором файлов.
- Флаг `joinPaymentDocs` работает как и раньше: если `true` — выпускается **один объединённый счёт** вместо двух.

### 1.3 Виды услуг и ставки НДС
Для каждого `Hotel` формируем до трёх позиций:
1) «Оплата Услуг HOOPS Service» — НДС 20%.
2) «Вознаграждение за выполнение поручения» — НДС 20%.
3) «Оплата HOOPS для выплаты Исполнителям» — **Без НДС**.
Количество в каждой позиции — `1 шт`. Строки с нулевой суммой **не включаются**.

### 1.4 Формат наименований строк
- Текст строго фиксированный, включающий **фирменное наименование объекта** из `Hotel` и **период** в формате:  
  `{ObjectName} Оплата Услуг HOOPS Service за период DD.MM.YYYY–DD.MM.YYYY`  
  `{ObjectName} Вознаграждение за выполнение поручения за период DD.MM.YYYY–DD.MM.YYYY`  
  `{ObjectName} Оплата HOOPS для выплаты Исполнителям за период DD.MM.YYYY–DD.MM.YYYY`

### 1.5 Итоговые суммы (общая формула)
- `with_vat_base` = сумма позиций с НДС (виды 1 и 2).
- `vat` = `with_vat_base * 0.20` (без доп. округлений сверх текущей реализации).
- `no_vat` = сумма позиций «Без НДС» (вид 3).
- `grand_total` = `with_vat_base + vat + no_vat`.
- Требование консистентности: **итоги УПД печатного вида, УПД XML, счёта(ов) и акта должны совпадать до копейки**.

## 2. Изменения по каждому файлу закрывающих документов

Ниже — задачи для доработки рендеров. **Контракты БД и API не меняем.** Все файлы сохраняются через действующий пайплайн сохранения и конвертации.

### 2.1 УПД (DOCX → PDF)

**Цель.** Единый УПД на группу объектов одного ИНН.

**Изменения.**
1) Табличная часть: вывести по каждому выбранному `Hotel` до трёх строк в порядке 1→2→3.  
   - Кол-во = `1`.
   - Ставка НДС: `20%` для (1, 2), «Без НДС» для (3).
   - Наименование — по шаблону из п.1.4.
2) Итоги:  
   - Итого без НДС (база под НДС) = сумма (1, 2).  
   - Сумма НДС 20% = `0.20 * база под НДС`.  
   - Строки «Без НДС» учитываются в «Всего к оплате», но не в «Сумма НДС».  
   - Пропись суммы — как в текущем шаблоне.
3) Дата документа (`closingDate`), номер, реквизиты — как сейчас.

**Технические пункты.**
- В рендере заменить одиночную тройку строк на цикл по `rows`.  
- Исключить строки с нулевыми суммами.
- Контрольная сверка: рассчитанные итоги УПД должны совпасть с итогами счёта(ов) и акта.

**Сохранение.**
- Создаём `ClosingDocumentFile` типа УПД с `name`, `path`, `amount=grand_total`, `number` — по текущей логике.

**Чек‑лист.**
- [ ] В каждой строке корректный объект и период.
- [ ] Ставки НДС соблюдены.
- [ ] Итоги и пропись совпадают с актом и счётом(ами).

---

### 2.2 УПД XML

**Цель.** Полное соответствие печатной форме УПД.

**Изменения.**
1) Табличная часть XML: на каждую позицию из DOCX создать узел с наименованием, количеством `1`, ставкой (`20%` или «Без НДС»), суммой без НДС, суммой НДС и суммой с НДС.  
2) Итоги в XML равны итогам печатного УПД до копейки.

**Технические пункты.**
- Использовать текущую схему и провайдера ЭДО. Версии и namespace не менять.
- Валидация XSD после генерации.
- При рассинхроне сумм — ошибка и откат.

**Сохранение.**
- Создаём/обновляем файл XML УПД рядом с печатной формой, с теми же номером и датой. Метаданные файла не меняются.

**Чек‑лист.**
- [ ] Количество и порядок позиций совпадают с DOCX.  
- [ ] Суммы и НДС равны печатной форме.  
- [ ] XML проходит валидацию схемы.

---

### 2.3 Счёт HOOPS (DOCX → PDF)

**Цель.** Счёт только по услугам HOOPS и вознаграждению.

**Изменения.**
1) Табличная часть: для каждого `Hotel` две строки:  
   - `… Оплата Услуг HOOPS Service …` — НДС 20%, `1 шт`.  
   - `… Вознаграждение за выполнение поручения …` — НДС 20%, `1 шт`.  
2) Итоги: `Итого без НДС`, `НДС 20%`, `Всего к оплате`, пропись — как сейчас.

**Технические пункты.**
- В рендере фильтровать `rows` по видам (1, 2).  
- Исключать нулевые строки.
- Итоги счёта должны входить в общий контроль консистентности.

**Сохранение.**
- `ClosingDocumentFile` типа счёта HOOPS. `amount` — «Всего к оплате» по данному счёту.

**Чек‑лист.**
- [ ] Две строки на каждый объект, корректные ставки.  
- [ ] Итоги совпадают с УПД и Актом по части с НДС.

---

### 2.4 Счёт Исполнители (DOCX → PDF)

**Цель.** Счёт по услугам Исполнителей.

**Изменения.**
1) Табличная часть: для каждого `Hotel` одна строка:  
   - `… Оплата HOOPS для выплаты Исполнителям …` — **Без НДС**, `1 шт`.  
2) Итоги: сумма строк, НДС = 0, «Всего к оплате» = сумма строк.

**Технические пункты.**
- В рендере фильтровать `rows` по виду (3).  
- Исключать нулевые строки.

**Сохранение.**
- `ClosingDocumentFile` типа счёта Исполнителей. `amount` — сумма строк.

**Чек‑лист.**
- [ ] Только строки «Без НДС».  
- [ ] Итоги совпадают с долей «Без НДС» в УПД/Акте.

---

### 2.5 Объединённый счёт (DOCX → PDF), если `joinPaymentDocs=true`

**Цель.** Один счёт вместо двух.

**Изменения.**
1) Табличная часть: объединить строки из п.2.3 и п.2.4 в одну таблицу.  
2) Итоги:  
   - база под НДС = сумма строк c 20%,  
   - НДС = 20% от базы,  
   - «Без НДС» — сумма строк вида (3),  
   - «Всего к оплате» = база + НДС + «Без НДС».

**Технические пункты.**
- Порядок строк: группировать блоками по `Hotel` (1→2→3).
- Исключать нулевые строки.

**Сохранение.**
- Создаётся ровно **один** `ClosingDocumentFile` счёта. Маска имени и место в массиве `files` — как в текущем режиме объединения.

**Чек‑лист.**
- [ ] Полный набор строк, верные ставки.  
- [ ] Итоги совпадают с УПД/Актом/XML.

---

### 2.6 Акт приёма‑передачи (DOCX → PDF)

**Цель.** Подтверждение оказанных услуг по группе объектов.

**Изменения.**
1) Табличная часть: для каждого `Hotel` до трёх строк:  
   - `… Услуги HOOPS Service …` — НДС 20%, `1 шт`.  
   - `… Вознаграждение за выполнение поручения …` — НДС 20%, `1 шт`.  
   - `… Услуги Исполнителей …` — **Без НДС**, `1 шт`.  
2) Итоги и пропись — как в текущем акте.

**Технические пункты.**
- Цикл по `rows`. Исключать нулевые строки.
- Итоги акта входят в контроль консистентности.

**Сохранение.**
- `ClosingDocumentFile` типа акта. `amount` — «Всего к оплате».

**Чек‑лист.**
- [ ] Три вида строк, ставки соблюдены.  
- [ ] Итоги совпадают с УПД/Счётами/XML.

## 3. Сервис сборки строк

**Функция:** `build_group_rows(hotels, startDate, endDate) -> rows, totals`

- Для каждого `Hotel` использовать текущие расчёты одиночного выпуска, получить суммы по трём видам услуг.
- Сформировать `rows` (объект, вид, qty=1, ставка НДС, суммы), удалить нулевые элементы.
- Посчитать `totals` по формуле из п.1.5.
- Возврат использовать всеми рендерами.

**Требование:** не менять сигнатуры существующих публичных функций. Новая функция — внутренняя, вызывается из текущих генераторов документов.

---

## 4. Контроль консистентности

- Перед сохранением сравнить итоги УПД (DOCX), УПД XML, счёта(ов) и акта: `with_vat_base`, `vat`, `no_vat`, `grand_total`.
- При несовпадении — ошибка и отмена генерации.
- Дополнительных округлений не вводить до отдельного решения.

---

## 5. Точки правки в проекте (ориентиры)

> Пути могут отличаться. Везде помечать вставки комментарием `# [GROUP-CLOSING-DOCS]`.

- `core/closing_documents/mutation.py` — интеграция `build_group_rows(...)` в место построения контента, проброс `rows` в рендеры; использование существующего `joinPaymentDocs` для объединённого счёта.
- `core/hotels/scripts/`:
  - `totals_service.py` или эквивалент — реализовать `build_group_rows` на основе одиночных расчётов.
  - `render_utd.py` — цикл по строкам, итоги.
  - `render_utd_xml.py` — табличная часть из `rows`, итоги = печатной форме.
  - `render_invoice.py` — режимы `hoops`/`contractors`/`combined`.
  - `render_act.py` — цикл по строкам, итоги.

Хранение в MinIO, создание `ClosingDocument` и `ClosingDocumentFile`, проставление `name/path/amount/number` — без изменений.

## 6. Тест‑план

1) **Полный набор**: 3 объекта, у каждого все три вида сумм > 0. Проверить число строк, тексты, ставки НДС, итоги, пропись; равенство печатных форм и XML.
2) **Пустые услуги Исполнителей** у одного объекта → строка «Исполнители» отсутствует во всех формах.
3) **Объединение счетов**: `joinPaymentDocs=true` → один счёт, `false` → два счёта; итоги совпадают.
4) **Разные ИНН** в выборе объектов → валидационная ошибка.
5) **Хранение**: файлы сохранены по текущему шаблону пути; `files { name, path, amount, number }` заполнены.
6) **Регресс**: одиночный выпуск на один объект не изменился.

---

## 7. Критерии приёмки

- Формулировки строк, период и порядок строго соответствуют шаблонам.
- Ставки НДС соблюдены: Service/Вознаграждение — 20%, Исполнители — Без НДС.
- Итоги и пропись совпадают между всеми формами и XML.
- API, модели и пути хранения не изменились.
- В режиме объединения счетов выдаётся ровно один счёт, содержащий все строки.
