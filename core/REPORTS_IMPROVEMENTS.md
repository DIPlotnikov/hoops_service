# Потенциальные ошибки и предложения по доработкам отчетов

Документ аккумулирует найденные потенциальные ошибки, спорные места и предложения по улучшению логики и UX отчетов. Используется как живой список задач и идей.

## Потенциальные ошибки / несоответствия

1) Стандартный отчет: расчет `cost_of_the_service_f`
- Файл/функция: `core/hotels/scripts/reports/standart_report.py` → `create_df`
- Текущая формула в ORM-аннотации:
  - `cost_of_the_service_f = F("full_hoops_f") - F("remuneration_of_the_service_t")`
- Ожидаемая формула (вероятно):
  - `cost_of_the_service_f = F("full_hoops_f") - F("remuneration_of_the_service_f")`
- Риск: неверное вычитание теоретического вознаграждения из фактической доли HOOPS приводит к искажению фактических сумм.
- Предложение: заменить `_t` на `_f` и покрыть кейсы тестами (сравнение строк fact/teor).

2) Текст статуса при отсутствии стопа работы
- Файл/функция: `core/hotels/scripts/reports/standart_report.py` → `create_df`
- Сейчас: и для отсутствия старта, и для отсутствия стопа используется «Не было старта работы».
- Предложение: для `stop_at__isnull=True` использовать «Не было стопа работы».

3) Округление `volume_time_f` вверх до сотых
- Формула: `Ceil((F("duration_f") * 100) / 3600000000) / 100`
- Риск: систематическое завышение фактического объема до ближайшей сотой.
- Предложение: обсудить политику округления (вверх/вниз/до ближайшего) и унифицировать с бизнес-правилами. Добавить юнит-тесты на граничные значения.

4) Приоритет описания услуги
- Сейчас используется `task__profession__description` даже если у персональной профессии есть свое описание.
- Предложение: если у `personal_profession` есть описание, приоритизировать его над обычной профессией.

## Улучшения и рефакторинг

1) Параметризация `remuneration`
- Сейчас `remuneration=10` зашито в сигнатуре `create_df`.
- Предложения:
  - Прокинуть параметр через GraphQL input (для администратора и менеджера) или
  - Читать из настроек (например, через модель настроек; аналогично `settings.models.get_remuneration()`).

2) Консолидация реализаций Стандартного отчета
- В проекте присутствуют две реализации: pandas (`standart_report.py`) и openpyxl (`excel_handler.ReportBuilder.create_manager_standart_report`).
- Предложение: оставить одну реализацию как единственный источник правды, а вторую удалить/законсервировать, либо привести к общему слою расчетов + отдельный слой рендеринга Excel.

3) Вынос бизнес-формул
- Вынести расчетные формулы (время, объем, суммы, HOOPS/вознаграждение) в отдельный модуль/сервис с юнит-тестами.
- Рендеринг в Excel держать отдельно (pandas/xlsxwriter или openpyxl), чтобы изменение бизнес-логики не влияло на верстку.

4) Улучшение статуса/проблемы
- Сделать словарь статусов/проблем (enum + локализация) и единый агрегатор приоритетов: комментарий-коррекция > несогласована > не было старта > не было стопа.

5) Диаграммы в PNG внутри репозитория
- Поддерживать `.mmd` исходники и обновлять PNG при изменениях, чтобы документация оставалась читаемой без внешних инструментов.

## Идеи для UX отчетов

- Добавить в шапку явный период (даты) и фильтры, которыми сформирован отчет (гостиница, менеджер, профессии).
- Вынести в подвале пояснение формул и округлений.
- Добавить ссылку на исходную заявку из ячейки «Номер заявки» (если используется в UI/внутреннем просмотрщике).
